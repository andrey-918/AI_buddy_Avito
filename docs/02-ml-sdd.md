# AI-buddy — SDD для поиска и ответа, черновик v0.1

Статус: **на обсуждении с командой**. Этот документ задаёт проверяемое поведение ML-части до выбора модели, эмбеддингов и порогов сходства. Первый рабочий сценарий — вопрос backend-стажёра о доступе к учебному репозиторию. Реальные внутренние маршруты Авито нам неизвестны; в демо они помечены как синтетические.

## 1. Что получает и возвращает помощник

Вход: текст вопроса, тестовая роль (`intern`, `mentor`, `manager`), разрешённый контекст команды и текущее время. В будущем роль и контекст придут из существующих систем Авито, а не из свободного выбора на экране.

Выход — ровно один из трёх исходов:

| Исход | Когда | Что видит пользователь |
| --- | --- | --- |
| `answer` | Найдена разрешённая, актуальная карточка с подтверждённым источником; вопрос не требует решения человека | Краткий ответ, точный источник, владелец, дата проверки, следующий шаг |
| `human_gate` | Требуется согласие/решение сотрудника, источник истёк или обнаружен конфликт сведений | Что нужно решить, кому передан вопрос, статус передачи и следующий шаг; без выдуманного решения |
| `fallback` | Нет подходящей карточки, вопрос вне области продукта, запрос нельзя безопасно обработать или сервис недоступен | Честное объяснение ограничения и безопасный следующий шаг; без предположений |

Пользователь задаёт вопрос своими словами; совпадение с заранее записанной формулировкой не требуется. Модель может понять вопрос и выбрать релевантные сведения из переданного ей контекста. Оценка сходства и уверенность модели помогают выбрать кандидата, но **сами по себе не подтверждают факт**. Даже очень похожая карточка не становится источником, если она `pending`, `expired`, недоступна роли или не имеет проверяемого происхождения.

## 2. Порядок обработки вопроса

1. Принять вопрос и локально проверить, относится ли он к исключённым темам или содержит чувствительные персональные/финансовые сведения. Если да — сразу вернуть `fallback` с кратким объяснением ограничения. Текст такого вопроса не сохранять и не отправлять внешнему AI API, включая API эмбеддингов.
2. Определить намерение: `onboarding`, `navigation`, `values`, `other`. Для сравнения начать с правил, затем проверить вариант с моделью на том же наборе вопросов.
3. До поиска отфильтровать знания по роли, команде, `approved`, допустимому происхождению и `expires_at`.
4. Подготовить контекст для модели. Сравнить два основных варианта: передать ей **все допустимые карточки** небольшой базы либо предварительно найти релевантные фрагменты и передать только их. Во втором варианте сравнить поиск по словам, эмбеддингам и их сочетание, затем ранжировать кандидатов.
5. Проверить, что выбранный фрагмент действительно отвечает на смысл вопроса. При поиске порог подбирать на размеченных примерах, включая вопросы без ответа. Низкая уверенность означает `fallback` или `human_gate`, а не догадку.
6. Применить правило Human Gate независимо от результатов поиска: AI может объяснить процедуру, но согласие, утверждение и иное решение остаются за сотрудником.
7. Сформировать короткий ответ только из допустимых карточек. LLM получает сам вопрос и отобранный контекст, находит в нём опору для ответа и формулирует ответ с ID источников. Проверить, что указанные ID действительно были переданы модели **и что фактические утверждения ответа следуют из фрагментов**: один только правильный ID не защищает от выдумки. При сбое модели показать доступную проверенную карточку без пересказа либо `fallback`.
8. Показывать действие как выполненное только после успешного ответа мок-сервиса. Записать обезличенные технические события, но не текст чувствительного вопроса.

Содержимое найденной веб-страницы или карточки — **данные, а не инструкции для AI или разрешение на действие**. Ссылки внутри них не дают права вызвать сервис или раскрыть информацию.

## 3. Какие источники допустимы

Каждая будущая карточка получает `id`, `title`, `evidence_text` (проверенный фрагмент источника), `answer` (краткое резюме), `category`, `source_url` или ID документа, точное место в источнике, `data_origin`, `status`, `owner_id`, `allowed_roles`, `team_scope`, `checked_at`, `updated_at`, `expires_at`. Возможные формулировки вопроса — **необязательные примеры** для оценки и подсказок, не ключ поиска. Значения `data_origin`: `case_fact`, `public_source`, `synthetic`, `mentor_verified`.

Правило использования:

- `approved` + неистёкший срок + разрешённая роль + проверяемый источник → допустимое основание ответа.
- `synthetic` → только в демо с явной пометкой «учебные данные»; не выдавать за регламент Авито.
- `pending`/`draft` → не использовать как подтверждённый ответ.
- `expired` → не использовать в ответе; отправить владельцу на проверку.
- Нет точной опоры в источнике → не превращать общий материал в инструкцию о внутреннем процессе.

Фрагмент чек-листа, присланный командой, задаёт структуру шагов. Он не подтверждает вымышленные имена, владельцев сервисов или конкретный порядок выдачи доступов. Демонстрационная инструкция `K-101` о репозитории остаётся `synthetic` до проверки реальным владельцем процесса.

## 4. Human Gate и действия

Human Gate обязателен, когда вопрос требует согласования, утверждения или решения конкретного человека; когда знания истекли/противоречат друг другу; либо когда прав пользователя недостаточно для действия. AI может показать допустимую процедуру и подготовить запрос, но само действие запускается после явного нажатия пользователя и проверок Go API. Отказ, ошибка или таймаут сервиса не отображаются как успех.

Для демонстрации доступа к репозиторию: ответ по `K-101` объясняет учебную процедуру; создание заявки возвращает ID и `waiting_mentor`; только решение наставника меняет статус на `approved` или `rejected`. Статус действия всегда берётся из мок-сервиса, не из текста модели.

## 5. Повторяющиеся вопросы и Knowledge Loop

Новый вопрос без ответа может стать кандидатом для базы знаний: вопрос → Human Gate → ответ наставника → `pending` → проверка владельцем → `approved` → повторное использование. Перед созданием карточки ищем точные и семантически похожие вопросы. Система показывает предполагаемые дубли владельцу; автоматически объединять карточки разных ролей, команд или с разными источниками нельзя.

Сроки для первого демо: Manifest — 180 дней, описание сервисов — 90, контакты/зоны ответственности/технические инструкции — 30, FAQ наставников — 60. За 7 дней до срока владелец получает уведомление. Без подтверждения запись становится `expired`; её можно отозвать раньше вручную.

## 6. Контрольные сценарии для следующего файла

| Вопрос или условие | Ожидаемый исход |
| --- | --- |
| «Как получить доступ к учебному репозиторию?», «Где взять права на код команды?» и другие перефразировки | `answer` по актуальной `K-101` с пометкой `synthetic`; заявка только после нажатия |
| «Кто отвечает за CI/CD?» | `answer`, только если разрешена и актуальна конкретная карточка ответственности |
| «Можно мержить без согласования?» | `human_gate` наставнику даже при наличии FAQ о процедуре |
| «Как устроен staging?» при истёкшей карточке | `human_gate` владельцу; старый ответ не показывать как действующий |
| Вопрос о неописанном внутреннем процессе | `fallback`, без реконструкции по публичным статьям |
| Ограниченная для роли карточка | Не раскрывать её содержание или метаданные; допустимый `fallback`/маршрут |
| Два противоречащих актуальных источника | `human_gate` владельцу, без выбора факта по более высокому score |
| Вопрос с чувствительными данными | Не сохранять текст и не посылать его внешней модели; безопасный `fallback` |
| Точный или смысловой дубль вопроса | Предложение объединения владельцу, без автоматического `approved` |
| Сбой эмбеддингов, LLM или мок-сервиса | Видимое ожидание и честный статус ошибки; никакого придуманного результата |

## 7. Как сравним подходы

Следующим файлом создаём фиксированный набор вопросов с правильным исходом, ожидаемым ID источника и ожидаемыми дублями. На нём сравниваем три схемы: (A) LLM читает всю маленькую разрешённую базу; (B) поиск выбирает фрагменты перед LLM; (C) гибридный поиск и ранжирование выбирают фрагменты перед LLM. Для B и C измеряем `Recall@3` и `MRR` поиска. Для всех схем — долю ответов с корректной опорой на источник, ошибки Human Gate, точность/полноту поиска дублей, задержку и стоимость обращения. Для продукта отдельно считаем подтверждённое решение обращения и отзыв «полезно/нет».

Числовые пороги сходства и целевые значения метрик зададим после первой разметки и baseline: маленький набор из четырёх карточек не позволяет честно выбрать их заранее. Каждую версию оцениваем на **одних и тех же** вопросах, а разбор ошибок сохраняем без чувствительного текста.

## 8. Решения для совместного выбора

1. Истёкшая карточка без назначенного владельца: направлять вопрос наставнику команды по умолчанию или показывать fallback с просьбой уточнить ответственного? При известном владельце вопрос передаётся ему, как задано в продуктовых правилах.
2. Ответ по публичному источнику: показывать его прямо в чате или сначала спрашивать, нужен ли именно контекст конкретной команды? Это важно, чтобы не смешать общие инженерные практики с локальными правилами.
3. При сбое LLM, но успешном поиске: показывать краткий текст карточки без генерации или всегда уходить в fallback? Первый вариант полезнее, второй строже; оба требуют проверенного источника.

## 10. Состояние реализации на 16.11.2026

- Живой чат вызывает Go `POST /api/chat`. Go проверяет вопрос через `ScreenQuestion`, фильтрует знания по роли, команде, статусу и TTL и только затем передаёт допустимые карточки в `ml/runtime.py`.
- Без ключа работает локальный BM25 с консервативным порогом 4,8 на текущем демонстрационном корпусе. Это эвристика, а не оценка вероятности или универсальная гарантия релевантности.
- При наличии `BUDDY_LLM_URL`, `BUDDY_LLM_MODEL`, `BUDDY_LLM_API_KEY` внешняя модель выбирает ID карточки или `null`. Сервер повторно проверяет выбранный ID и показывает **готовый утверждённый ответ карточки**. Свободная генерация ответа с проверкой всех фактических утверждений пока не включена: такой вариант требует отдельной проверки на галлюцинации.
- Human Gate для согласований и устаревшего staging срабатывает до выбора источника. Для неизвестного вопроса возвращается fallback.
- `ml/duplicates.py` предлагает похожие карточки перед утверждением нового FAQ. Это подсказка наставнику, не автоматическое объединение.
- Ответ наставника сохраняется как `pending`, после утверждения становится доступен на 60 дней. Истёкший или отозванный ответ исключается из ML-контекста. За семь дней до истечения на экране наставника появляется напоминание; внешние уведомления не отправляются.
- Локальные эмбеддинги и гибридное ранжирование есть как эксперименты в `ml/embedding_retrieval.py` и `ml/compare_retrieval.py`; рабочий чат пока использует BM25 либо выбор источника внешней LLM. Решение о включении гибридного поиска следует принимать по оценке на размеченном наборе.
- Обезличенные события сохраняются в демо-состоянии: тип, случайный ID обращения, роль, категория, статус, ID источника, причина и серверное время. Текст вопроса в аналитике не хранится. Руководитель видит счётчики обращений, ответов, передач и полезности. `Successful Resolution Rate` пока не выводится как итоговая метрика, поскольку для неё нужно надёжно связать ответ с подтверждённым результатом действия или передачи.
