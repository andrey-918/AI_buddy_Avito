# AI-buddy — спецификация поведения v0.3

SDD (Specification-Driven Development) означает, что до реализации мы описываем наблюдаемое поведение: вход, допустимые источники, решение, действие, результат и ошибки. Затем по этой спецификации пишем код и проверяем сценарии. Этот файл — первый небольшой контракт, который будем уточнять вместе.

## Реализовано к концу второго этапа

Кликабельный интерфейс с выбором роли: стажёр, наставник, руководитель. Для стажёра доступны недельное погружение, чат, задачи, сервисы и команда. Наставник видит список подопечных и очередь вопросов, руководитель — состав команды. Главный сценарий — запрос доступа к учебному backend-репозиторию через имитацию корпоративного сервиса. Сценарий опытного сотрудника запланирован на отдельный этап.

Данные, имена и инструкции в прототипе синтетические. Каталог содержит названия сервисов из кейса, но не их настоящие данные. Шаги первой недели адаптированы из присланного фрагмента чек-листа. Задачи по ревью работы, ИПР и развивающей обратной связи остаются за наставником и не входят в функции AI-buddy. Настоящая корпоративная авторизация, LLM и корпоративные интеграции пока не подключены.

Выбор роли в демо меняет экраны и создаёт временный тестовый контекст пользователя. Go API сверяет роль при каждом действии и возвращает `403` для запрещённого действия. Выбор роли свободный и не доказывает личность сотрудника. В реальной среде готовая система Авито предоставит идентичность и роль; AI-buddy не создаёт отдельный логин или HR-систему.

## Контракт ответа AI

1. Определить намерение: `onboarding`, `navigation`, `values`, `other`.
2. Проверить права на категорию знания и действия.
3. Ответить только по записи со статусом `approved`, подтверждённым источником и неистёкшим `expires_at`. Синтетический источник допустим только в демонстрации и маркируется.
4. Показывать источник, владельца и дату проверки рядом с ответом.
5. Если требуется решение человека, создать `human_gate` и показать ответственного и следующий шаг.
6. Если подходящего подтверждённого знания нет, показать fallback. Не достраивать ответ догадками.
7. `pending` и `expired` не служат основанием для ответа.

## База знаний: состояние и следующий этап

Сейчас настоящей базы знаний нет: четыре синтетические карточки находятся прямо в `dist/app.js`. Формулировки распознаются простыми правилами по ключевым словам. Модель и семантический поиск не подключены.

На следующем этапе соберём отдельную JSON-базу. Публичные материалы из кейса, включая AvitoTech Playbook, дадут проверяемые сведения о ценностях и открытых инженерных практиках. Присланный фрагмент чек-листа даст структуру шагов адаптации. Внутренние маршруты, доступы и контакты, которых нет в открытом источнике, останутся синтетическими до проверки владельцем. Каждая карточка получит ссылку или идентификатор источника, статус, владельца и срок действия.

Повторяющиеся вопросы нужно обнаруживать до создания новой карточки: сначала нормализация текста и точные совпадения, затем семантическая близость. Похожие вопросы показываются владельцу как кандидаты на объединение. Автоматически утверждать новый ответ или сливать карточки разных ролей и контекстов нельзя.

## Главный сценарий: доступ к репозиторию

**Участники:** стажёр, наставник, имитация сервиса доступов.

**Предусловие:** стажёр видит синтетическую инструкцию `K-101`, разрешённую для роли backend intern.

**Путь:**

1. Стажёр спрашивает, как получить доступ к репозиторию.
2. AI показывает короткую инструкцию, источник, дату проверки и кнопку «Создать запрос».
3. При нажатии имитация сервиса создаёт заявку с уникальным ID и статусом `waiting_mentor`. UI показывает результат и следующий шаг.
4. Наставник в своей очереди подтверждает запрос. Имитация сервиса меняет статус на `approved`. UI показывает обновлённый статус.
5. Повторная отправка той же заявки не создаёт дубль.

**Критерии приёмки:** действие возвращает ID и статус; состояние переживает перезагрузку; стажёр видит следующий шаг; запрос нельзя подтвердить от лица стажёра ни в интерфейсе, ни через Go API. Переключатель роли остаётся частью демо, а не настоящей проверкой личности.

## Имитация корпоративных сервисов на бэкенде

Браузерная имитация заявки заменена локальным HTTP-моком за Go API. В одном тестовом сервере сейчас собраны две независимые имитации: сервис заявок на доступ и чек-лист новичка с целями адаптации. Это не копия конкретной системы Авито. Интерфейс предлагает действие, пользователь подтверждает его, Go-бэкенд проверяет демо-роль и параметры, вызывает мок и возвращает его фактический результат. Интерфейс не объявляет действие выполненным до ответа сервиса. Мок доступен только на локальном адресе процесса и требует внутренний токен.

Минимальный контракт сервиса доступов:

| Операция | Вход | Выход |
| --- | --- | --- |
| Создать заявку | обезличенный ID стажёра, ID ресурса, ключ идемпотентности | ID заявки, `waiting_mentor`, следующий шаг |
| Получить статус | демо-сессия | актуальная заявка в `GET /api/bootstrap` |
| Решение наставника | ID заявки, `approve` или `reject`, роль наставника | `approved` или `rejected`, время решения |

Повторная отправка с тем же ключом не создаёт новую заявку. Недоступный ресурс, неверная роль, отказ или сбой сервиса возвращают явный статус ошибки; интерфейс показывает его без придуманного успеха. Содержимое чувствительных запросов в аналитику не попадает. Проверка роли выполняется в Go API; мок-сервис проверяет внутренний токен и допустимые значения операции.

## План адаптации и цели первой недели

Руководитель задаёт ожидания и предлагает конкретные цели адаптации после обсуждения со стажёром. AI-buddy помогает записать согласованный план и показывает статусы основных организационных шагов. Он не создаёт OKR за руководителя, не оценивает качество работы, не проводит ревью и не даёт развивающую обратную связь.

Состояния плана: `draft` → `awaiting_intern` → `agreed`; при несогласии стажёра — `changes_requested` и обсуждение с руководителем. Сейчас мок хранит ID выбранных целей, статус, ID синтетического контекста OKR и время изменения. Интерфейс маркирует этот контекст как демо; AI не генерирует OKR. В рабочей версии понадобятся владелец целей, согласовавшие стороны, срок и проверенный источник OKR.

Для проверки сценария используем имитацию API чек-листа новичка: руководитель сохраняет одну–три синтетические цели и ссылку на синтетический контекст OKR, стажёр подтверждает предложенный план или просит правки, затем отмечает организационный шаг. API возвращает обновлённый статус; интерфейс показывает следующий шаг. Руководитель видит ход основных шагов, но не получает автоматическую оценку стажёра.

Критерии приёмки: только руководитель может предложить или изменить цели; стажёр может подтвердить план или запросить правки; несогласованный план не показывается как утверждённый; статус шага меняется только после результата мок-сервиса; отсутствие ответа сервиса не превращается в завершённый шаг.

## Другие демонстрационные ветки

| Запрос | Ожидаемое поведение |
| --- | --- |
| Кто отвечает за CI/CD? | Навигационный ответ с источником и контактом команды. |
| Можно ли мержить без согласования? | Human Gate: передача наставнику, без самостоятельного решения AI. |
| Как устроен staging? | Истёкшая карточка, ответ не показывается; Human Gate владельцу. |
| Неизвестный вопрос | Fallback без выдуманного ответа. |

## Knowledge Loop и срок действия

Вопрос → Human Gate → ответ наставника → `pending` → проверка → `approved` → повторное использование. Наставник может объединить дубли, назначить владельца, подтвердить или отозвать ответ. Для демонстрации используем TTL: manifest — 180 дней; сервисы — 90; контакты, зоны ответственности и технические инструкции — 30; FAQ наставников — 60. За 7 дней до истечения нужно уведомление владельцу. Без подтверждения запись становится `expired` и перестаёт быть источником для AI.

Минимальная карточка: `id`, вопрос, краткий ответ, категория, `source`, `data_origin`, `status`, `owner_id`, `created_at`, `updated_at`, `checked_at`, `expires_at`. В следующем этапе вынесем записи из UI в JSON-базу и добавим проверяемые правила поиска, дедупликации и TTL.

## Данные и аналитика

Не сохраняем текст чувствительных запросов, персональные или финансовые сведения. Go-сервер сохраняет синтетические ID и статусы заявки, выбранные цели и отметки шагов в локальном JSON-файле. Демо-ответы наставника и передачи человеку пока хранятся только в браузере. События аналитики в следующем этапе должны содержать обезличенный ID, роль, категорию, статус и техническое время; текст вопроса в события не входит.
