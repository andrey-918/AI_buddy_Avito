# AI-buddy — помощник для адаптации и рабочего контекста

AI-buddy — демонстрационный прототип для Hack&Change. Он показывает, как стажёр может найти проверенную инструкцию, выполнить организационное действие через мок-сервис, а при необходимости передать вопрос человеку. Для наставника предусмотрены очередь заявок и пополнение FAQ; руководитель может подготовить план адаптации и увидеть обезличенные счётчики обращений.

**Это не подключённый к Авито корпоративный сервис.** Имена, роли, команда, база знаний, заявки и регламенты в демо синтетические. Реальные системы Авито не вызываются; заявка на доступ обрабатывается локальной имитацией API.

## Как проверить решение

Для быстрой проверки достаточно:

1. Запустить прототип по инструкции ниже.
2. Открыть <http://127.0.0.1:4173> и выбрать роль **Стажёр**.
3. Нажать **«Открыть сценарий»**: помощник найдёт учебную карточку `K-101` и покажет источник.
4. Нажать **«Создать заявку»**: появятся ID заявки и статус ожидания наставника.
5. Переключить роль на **Наставник** и подтвердить заявку в очереди.
6. Вернуться к роли **Стажёр** и проверить обновлённый статус и следующий шаг.

То же прохождение записано в [видеодемонстрации](./recordings/ai-buddy-demo-2026-11-16T08-35-42Z.webm). В видео видны плавно движущийся указатель и подсветка кликов. **Видео показывает главный сквозной сценарий, а не все экраны прототипа**; остальные сценарии и способы проверки описаны ниже.

## Запуск

### Локально

Требуются Go 1.22+ и Python 3.10+. Из корня проекта:

```bash
go run ./cmd/buddy
```

Откройте <http://127.0.0.1:4173>. Чтобы выбрать другой порт:

```bash
PORT=4174 go run ./cmd/buddy
```

Состояние мок-сервиса по умолчанию сохраняется в `data/mock-state.json`. Для отдельной чистой демо-сессии можно задать свой файл:

```bash
BUDDY_DATA_FILE=data/demo-fresh.json go run ./cmd/buddy
```

Этот файл создаётся при выполнении действий и не содержит исходный текст чувствительных вопросов. Не удаляйте и не перезаписывайте файл состояния, если хотите сохранить результаты предыдущего демо.

### Docker

При установленном Docker Compose приложение собирается и запускается одной командой:

```bash
docker compose up --build
```

Затем откройте <http://127.0.0.1:4173>. Состояние контейнера хранится в Docker volume.

## Что происходит в видеодемонстрации

Запись [ai-buddy-demo-2026-11-16T08-35-42Z.webm](./recordings/ai-buddy-demo-2026-11-16T08-35-42Z.webm) показывает полный цикл одной заявки:

1. **Выбор роли стажёра.** Открывается домашний экран первой недели адаптации.
2. **Вопрос о доступе.** Стажёр открывает сценарий доступа к учебному backend-репозиторию.
3. **Поиск подтверждённого знания.** Чат показывает ответ по карточке `K-101`, её источник, владельца, даты проверки и окончания срока действия, а также пометку о синтетических учебных данных.
4. **Явное подтверждение действия.** Стажёр нажимает **«Создать заявку»**. Локальный мок-сервис возвращает уникальный ID и `waiting_mentor`; интерфейс показывает, что следующий шаг — согласование наставником.
5. **Решение сотрудника.** Наставник переключается в свою роль, видит заявку в очереди и нажимает **«Подтвердить»**. Статус меняет API, а не текст ответа модели.
6. **Обратная связь стажёру.** Стажёр возвращается в чат и видит подтверждённый статус и следующий шаг — настройку окружения.

Для чистой повторной записи используется скрипт:

```bash
npm install
npx playwright install chromium
npm run record:demo
```

Скрипт собирает Go-сервер, запускает его на свободном локальном порту с временным чистым файлом состояния и записывает браузерный сценарий. Рабочий `data/mock-state.json` не меняется. Результат сохраняется в `recordings/`: MP4, если установлен `ffmpeg`, иначе WebM. Путь можно задать явно:

```bash
npm run record:demo -- --output /tmp/ai-buddy-demo.webm
```

## Другие сценарии прототипа

Для демонстрации дополнительных функций переключайте тестовую роль в правом верхнем углу. Роль свободно выбирается только для демо и не является проверкой личности.

### 1. Ответ с источником и действие — стажёр

**Путь:** **Стажёр** → домашний экран → **«Открыть сценарий»** → **«Создать заявку»**.

- Чат ищет карточку в разрешённой базе и показывает готовый ответ из неё, источник, владельца, дату проверки и TTL.
- Синтетическая инструкция помечена как учебная; её нельзя принимать за реальный внутренний регламент Авито.
- Заявка создаётся только после нажатия пользователя. До успешного ответа мок-сервиса интерфейс не показывает действие как выполненное.
- Повторная отправка не создаёт вторую заявку: используется один и тот же ключ идемпотентности для тестового пользователя и ресурса.

### 2. Human Gate: решение остаётся за человеком

**Путь:** стажёр открывает чат и выбирает подсказку **«Нужно согласование?»**. Для запроса «Можно ли мержить без согласования?» помощник не отвечает «да» или «нет», а объясняет, что решение должен принять наставник. После **«Передать вопрос»** создаётся передача наставнику; в его очереди можно нажать **«Принять»**.

Для вопроса **«Как устроен staging?»** демонстрируется истёкшая инструкция: актуальный ответ не выдаётся, вопрос направляется владельцу темы Platform Tools. Это показывает разницу между ответом по действующей карточке и эскалацией владельцу.

### 3. Fallback и безопасный отказ

Задайте в чате вопрос о процессе, которого нет в базе. Если подтверждённого источника не найдено, помощник честно сообщает об ограничении и предлагает передать вопрос наставнику — он не должен реконструировать внутренние правила по догадке.

Запросы с распознанными чувствительными персональными или финансовыми данными и исключёнными темами блокируются локальной проверкой в Go до вызова Python/внешней модели. Для таких отказов текст чувствительного вопроса не сохраняется; кнопка передачи не предлагается.

### 4. Knowledge Loop и FAQ наставника

**Путь:** переключить роль на **Наставник** → заполнить форму **«Память наставника»** → добавить типовой вопрос и ответ.

- Новый ответ сохраняется со статусом `pending`, а не становится автоматически подтверждённым знанием.
- Поиск дублей показывает наставнику похожие карточки как подсказки; автоматически объединять или утверждать их система не должна.
- Кнопка **«Проверить и утвердить»** переводит ответ в `approved` на 60 дней. После этого ответ может попасть в контекст поиска чата.
- Ответ можно отозвать. Просроченный или отозванный FAQ не считается действующим основанием для ответа.

### 5. План первой недели и цели адаптации

**Путь:** роль **Руководитель** → выбрать одну–три цели → **«Сохранить черновик»** → **«Отправить стажёру»**; затем переключиться на **Стажёр** и согласовать план или запросить правки.

- План проходит состояния `draft` → `awaiting_intern` → `agreed` либо `changes_requested`.
- Стажёр может отмечать шаги первой недели; статус сохраняется через API и остаётся после перезагрузки.
- Цели и OKR в демо синтетические. Помощник не генерирует цели и не оценивает работу стажёра.

### 6. Каталог, команда и аналитика

- **Стажёр → Моя неделя:** пять дней адаптации с организационными шагами и прогрессом.
- **Сервисы:** демонстрационный каталог; реально выполняется только заявка на доступ к учебному репозиторию. Остальные строки — справочная навигация, не интеграции с корпоративными сервисами.
- **Команда:** синтетические участники и владельцы тем.
- **Руководитель:** состав команды, план адаптации и счётчики обращений, ответов с источником, передач, принятых вопросов и оценок полезности.

## Как работает поиск и защита данных

1. Браузер отправляет вопрос в Go API `POST /api/chat`.
2. Go локально применяет `ScreenQuestion`, проверяет роль и формирует разрешённый контекст из актуальных карточек до вызова ML.
3. Python-код `ml/runtime.py` ищет ответ локальным BM25. Сходство — эвристический score, не вероятность истинности.
4. Если BM25 находит подходящую карточку, Go повторно проверяет её ID и показывает готовый утверждённый ответ карточки, а не свободно сгенерированный текст.
5. Для решения сотрудника или истёкшей темы применяется Human Gate; при отсутствии опоры — fallback.
6. Только после явного действия пользователя Go API вызывает локальный мок-сервис. Мок проверяет допустимые значения, роль проверяет Go API, состояние записывается в JSON.

Без внешних ключей приложение работает на локальном BM25. Эксперименты с эмбеддингами и гибридным ранжированием находятся в `ml/`, но не являются поиском основного чата по умолчанию.

### Внешняя модель — необязательно

По умолчанию внешний провайдер не вызывается. При необходимости можно включить совместимый API, задав в том же терминале `BUDDY_LLM_URL`, `BUDDY_LLM_MODEL` и `BUDDY_LLM_API_KEY`. Внешняя модель выбирает ID карточки; сервер перепроверяет выбор и показывает ответ из карточки. Она не имеет права принимать решение за наставника или выполнять действие.

Для DeepSeek endpoint Chat Completions используется адрес и имя модели из официальной документации провайдера:

```bash
export BUDDY_LLM_URL='https://api.deepseek.com/chat/completions'
export BUDDY_LLM_MODEL='deepseek-chat'
printf 'Вставьте API key: '
read -s BUDDY_LLM_API_KEY
echo
export BUDDY_LLM_API_KEY
go run ./cmd/buddy
```

Перед запуском проверьте актуальные имена модели, условия тарификации и баланс на стороне провайдера. Скрипт записи наследует переменные окружения. Чтобы **обязательно** записать именно сценарий с реальным ответом DeepSeek и не получить видео локального BM25 по ошибке, выполните в том же терминале:

```bash
npm run record:demo -- --require-llm
```

Флаг `--require-llm` проверяет наличие endpoint, модели и ключа, а во время записи подтверждает, что интерфейс показывает источник, выбранный моделью. Видеозапись остановится с ошибкой, если проверка не прошла. Секреты нельзя добавлять в исходники, `.env.example`, видео или архив сдачи. Не вводите в демо реальные персональные, финансовые или конфиденциальные данные.

## Тесты и покрытие

Запустить все Go-тесты и создать отчёт покрытия:

```bash
go test ./... -coverprofile=coverage.out
go tool cover -func=coverage.out
```

В последней строке отчёта показан общий процент покрытия **Go-кода**; HTML-отчёт:

```bash
go tool cover -html=coverage.out
```

На момент подготовки демо Go-покрытие составляет **85,2%**. Это показатель операторов Go-пакетов, а не совокупное покрытие Go, Python и браузерного JavaScript.

Python unit-тесты:

```bash
python3 -m unittest discover -s ml -p 'test_*.py'
```

Оценочные скрипты retrieval можно запускать отдельно:

```bash
python3 ml/evaluate_retrieval.py
python3 ml/compare_retrieval.py
python3 ml/evaluate_full_context.py
```

Последняя команда работает без обращения к модели. Вызов внешней модели для одного оценочного примера выполняется только при настроенных ключах:

```bash
python3 ml/evaluate_full_context.py --run --case V2-D01
```

## Архитектура и файлы проекта

```text
Браузер (dist/)
    │ HTTP / JSON
    ▼
Go API (cmd/buddy/)
    ├── guardrails и проверка роли
    ├── база знаний и фильтрация доступа/TTL (internal/knowledge/)
    ├── поиск источника через Python (ml/runtime.py)
    └── локальный мок API (internal/mockcorp/)
             └── состояние заявок, FAQ, плана и событий в JSON
```

- `cmd/buddy/` — HTTP API, сессии демо, чат и маршруты действий.
- `internal/assistant/` — локальные guardrails чувствительных и исключённых запросов.
- `internal/knowledge/` — загрузка, валидация, фильтрация базы по статусу, роли, команде и сроку действия.
- `internal/mockcorp/` — локальный HTTP-мок заявки на доступ, передачи человеку, FAQ, плана и шагов.
- `ml/runtime.py` — классификация и выбор источника через BM25 либо настроенную внешнюю модель.
- `ml/duplicates.py` — подсказки похожих карточек при создании FAQ.
- `ml/embedding_retrieval.py`, `ml/compare_retrieval.py` — экспериментальные варианты retrieval.
- `data/knowledge.json` — карточки знаний с источником, статусом, областью доступа и TTL.
- `data/eval/` — фиксированные вопросы для оценки поведения поиска и guardrails.
- `dist/` — статические HTML/CSS/JavaScript интерфейса; отдельный frontend build не нужен.
- `docs/01-sdd.md`, `docs/02-ml-sdd.md` — спецификации сценариев и ML-поведения.
- `scripts/record-demo.mjs` — автоматизированная запись главного пользовательского сценария.

## Границы прототипа

- Все данные, участники, команда и внутренние процедуры в демо синтетические; прототип не является источником реальных правил Авито.
- Выбор роли — демонстрационный переключатель, не корпоративная аутентификация.
- Доступ к репозиторию и другие действия не отправляются в реальные системы: за Go API работает локальный мок.
- Внешняя LLM необязательна и не включена по умолчанию; подключение провайдера не делает его ответы официальной позицией компании.
- Проверка чувствительности основана на правилах и не заменяет промышленную DLP.
- Аналитика обезличена и не включает текст вопроса; достоверный `Successful Resolution Rate` не заявляется, поскольку для него нет надёжной связи между вопросом и подтверждённым результатом.
- Календарь, полноценный HR-процесс, оценка работы, ревью кода и ИПР не реализуются.
